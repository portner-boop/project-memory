# 02 — Модель документации

Как устроены сами файлы и почему именно так.

---

## Проблема с обычным `architecture.md`

Файл на 600 строк. Агент меняет логику refresh-токена. Что происходит:

1. Агенту грузят **весь файл** — 600 строк в контекст.
2. Он возвращает **весь файл целиком** с одним изменённым абзацем.
3. По дороге «улучшил» три абзаца, которых не просили.
4. В diff 40 изменённых строк вместо 3, ревьюить невозможно.

## Решение: адресуемые блоки

```md
---
id: ARCH-AUTH                      # адрес документа
type: architecture
code_paths:
  - backend/app/auth/**            # ЗА КАКОЙ КОД отвечает документ
last_verified_commit: a91d2f4      # когда сверяли с кодом
---

## Обновление токена
<!-- block: AUTH.REFRESH_TOKEN -->   # адрес куска внутри документа

Refresh token хранится в HTTP-only cookie.
Основная реализация: `backend/app/auth/service.py#AuthService.refresh`.
```

Теперь агент говорит не «вот новый файл», а **«замени блок `AUTH.REFRESH_TOKEN`
на вот это»**. В контекст грузится один блок, обратно приходит один блок,
в diff — три строки.

### Три поля, которые делают всю работу

| Поле | Зачем |
|---|---|
| `id` | постоянный адрес. Текст переписали, файл переехал — адрес живёт |
| `code_paths` | **самое важное поле.** Связь «документ ↔ код» |
| `symbols` | необязательное. Точная связь по графу, см. [07](07-codegraph.md#новое-поле-во-frontmatter-symbols) |
| `last_verified_commit` | маркер свежести. Давно не сверяли — не ошибка, но сигнал |

`code_paths` — это то, по чему система понимает: изменился
`backend/app/auth/login.py` → задет `ARCH-AUTH` → а `PRODUCT-REPORTS` не задет,
не трогаем.

Маски путей — грубый инструмент: они пропускают транзитивные зависимости
(поменяли общий хелпер в `common/`, а задет документ про отчёты). Если рядом
стоит [CodeGraph](07-codegraph.md), связь дополнительно ищется по графу вызовов.

### Правила именования

- Документ: `SCREAMING-KEBAB` — `ARCH-AUTH`, `PRODUCT-REPORTS`.
- Блок: `SCOPE.NAME` — `AUTH.REFRESH_TOKEN`.
- **ID не переименовываются.** На них ссылаются индекс, ADR и задачи.

## Ссылки на код: путь и символ

```text
❌ backend/app/auth/service.py:142      протухнет на первом рефакторинге
✅ backend/app/auth/service.py#AuthService.refresh
```

Второй вариант **проверяется скриптом**: открыть файл, поискать символ.
Не нашёлся — документация врёт, `/docs-check` ругается. Номер строки так не
проверишь.

> Внутри `deep-dive.md` конкретной задачи номера строк уместны — это
> одноразовый документ, описывающий код на момент разбора. В **постоянной**
> документации — только `path#Symbol`.

## ADR — журнал решений

Код показывает **как работает** система. Он никогда не показывает **почему так
решили**.

Через полгода ты смотришь на очередь на Redis Streams и думаешь «почему не
Celery?». Код ответа не содержит. Через час раскопок ты либо вспоминаешь, либо
переписываешь на Celery и наступаешь на те же грабли.

```md
---
id: ADR-014
status: accepted
task: ABSHTRUE-612
date: 2026-07-24
---

# Использовать Redis Streams вместо Celery

## Контекст
Нужна очередь обработки документов без отдельной Celery-инфраструктуры.

## Решение
Использовать Redis Streams и отдельный Python worker.

## Последствия
Плюсы: меньше инфраструктуры; Redis уже используется проектом.
Минусы: retry и dead-letter механику нужно реализовать самостоятельно.
```

### Когда создавать

**Только на настоящее решение.**

| Создавать | Не создавать |
|---|---|
| выбор технологии, библиотеки, хранилища | переименование переменной |
| отказ от ранее принятого подхода | вынос функции в модуль |
| смена архитектурной границы | добавление теста |
| осознанная пауза («решили не делать») | форматирование |

Иначе `decisions/` превращается в свалку и её перестают читать.

Статусы: `proposed` → `accepted` → `superseded` / `rejected` / `on-hold`.
`/docs-check` находит конфликты — два `accepted` по одному предмету.

**Откуда берётся шаблон.** `/docs-init` кладёт
[`docs/decisions/README.md`](../examples/demo-project/docs/decisions/README.md) —
объяснение, зачем это нужно, — и
[`docs/decisions/_template.md`](../examples/demo-project/docs/decisions/_template.md) —
болванку. Новый ADR заводится либо руками копированием шаблона, либо агентом
через операцию `create_adr` во время `/docs-sync`.

## `_index.json` — карта для агента

Выжимка всех frontmatter в один файл:

```json
{
  "ARCH-AUTH": {
    "path": "docs/architecture/auth.md",
    "code_paths": ["backend/app/auth/**"],
    "blocks": ["AUTH.ACCESS_TOKEN", "AUTH.REFRESH_TOKEN"]
  }
}
```

Агент читает **один** этот файл (пара килобайт) и знает всю карту документации,
не открывая ни одного документа. Дальше открывает только те, чьи `code_paths`
пересеклись с diff.

Строится скриптом за пятьдесят строк. **Модель тут не нужна.** Общий принцип:
детерминированное считаем кодом, LLM — только там, где надо понять смысл текста.

Коммитим в git: агент читает индекс сразу, а ревьюер видит в diff, что
структура документации изменилась.

```text
│
├── .repomind/

│   └── dirty                  # маркер «были правки»

    │
    ├── requirements/
    │   ├── inbox/             # СЮДА кидаешь .docx с ТЗ
    │   └── original/          # обработанные ТЗ, не редактируются
    │
    ├── tasks/
    │   └── ABSHTRUE-657/
    │       ├── request.md         # ТЗ в markdown
    │       ├── deep-dive.md       # технический разбор + план
    │       ├── estimate.md        # оценка в часах
    │       ├── summary.md         # короткое человеческое описание
    │       ├── progress.md        # ход работы
    │       └── result.md          # что в итоге сделали
    │

```

## Runbook — инструкции по запуску

Отдельный тип документа (`type: runbook`) для всего, что отвечает на вопрос
**«как это делать руками»**: поднять с нуля, прогнать тесты, накатить миграцию,
починить, когда сломалось, выкатить релиз.

```text
docs/runbook/
├── setup.md            RUN-SETUP     первый запуск, 20 минут для нового человека
├── daily.md            RUN-DAILY     тесты, линтеры, миграции, локальные команды
├── troubleshooting.md  RUN-TROUBLE   симптом → причина → что делать
└── release.md          RUN-RELEASE   порядок выкатки, чеклист, откат
```

Пример целиком — [demo-project/docs/runbook/](../examples/demo-project/docs/runbook/).

### Зачем это отдельный тип, а не «ещё один md»

**1. Это единственный источник правды по командам.** Агент не угадывает
`npm test` и не изобретает `pytest -k`, а берёт команду из `RUN-DAILY`.
В `AGENTS.md` — только ссылка, не сами команды.

**2. Это дешевле, чем держать в `AGENTS.md`.** Правила из `AGENTS.md` грузятся
в **каждую** сессию и едят контекст постоянно. Полная инструкция по запуску там
не нужна: она понадобится раз в месяц. Runbook подтягивается по требованию.

```text
AGENTS.md    3–5 самых опасных ловушек        грузится всегда
runbook/     всё остальное, подробно          грузится по надобности
```

**3. Команды можно проверять.** `/docs-check` умеет сверить упомянутые
команды с реальностью: есть ли такой make-таргет, есть ли такой скрипт в
`package.json`, существует ли management-команда. Протухшая команда в инструкции
хуже её отсутствия — человек тратит время на то, чего давно нет.

### Формат troubleshooting

Каждая запись строго по схеме **симптом → причина → что делать**:

```md
## PDF не генерируется, backend отдаёт 502
<!-- block: TROUBLE.PDF_502 -->

**Причина в 9 случаях из 10:** неверный `PDF_SERVICE_URL`.

| Откуда запущен backend | Куда должен смотреть |
|---|---|
| docker → docker | `http://pdf-service:8001` |
| хост → docker  | `http://localhost:8001` |
```

Заголовок — **симптом**, а не название проблемы. Человек ищет по тому, что
видит на экране, а не по тому, как это правильно называется.

Правило пополнения простое: **потратил больше получаса на непонятное — запиши**.
Это единственный документ, который выгодно вести реактивно, а не заранее.

### Подсказки: где что живёт

| Что | Куда | Почему |
|---|---|---|
| 3–5 ловушек, на которых теряют день | `AGENTS.md` | нужны всегда, стоят копейки |
| ловушка конкретного модуля | блок в его `architecture/` документе | приедет вместе с документом |
| «сломалось, что делать» | `runbook/troubleshooting.md` | ищут по симптому |
| «почему так сделано» | `decisions/` (ADR) | это решение, а не подсказка |

Главное — **не дублировать**. Ловушка живёт в одном месте, остальные ссылаются.

### Организующая идея: время жизни

```text
requirements/original/   НИКОГДА не меняется    ← что просили изначально
product/ architecture/   живёт годами           ← как система работает
contracts/               живёт годами           ← API
decisions/               только дописывается    ← почему так решили
runbook/                 меняется с процессом   ← как это делать руками
tasks/<ID>/              живёт недели           ← как делали задачу
now/current-task.md      живёт часы             ← что прямо сейчас
```

Сверху вниз — от вечного к сиюминутному. Правило: **чем выше, тем реже трогаем.**

### Почему `requirements/original/` не редактируется

- `requirements/original/` — что попросили, слово в слово.
- `tasks/<ID>/deep-dive.md` — что выяснили по ходу.

Разделив, через год честно увидишь, насколько итог разошёлся с ТЗ.
Смешаешь — эта информация теряется навсегда.

### Состав папки задачи

| Файл | Кто пишет | Когда |
|---|---|---|
| `request.md` | `/docs-task` | при заведении |
| `deep-dive.md` | `/docs-plan` | планирование |
| `estimate.md` | `/docs-plan` | планирование |
| `summary.md` | `/docs-plan` | планирование |
| `progress.md` | агент | во время разработки |
| `result.md` | `/docs-sync` | после реализации |

`/docs-check` проверяет, что обязательные файлы на месте.
