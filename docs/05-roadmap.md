# 05 — Что делать и в каком порядке

---

## Версия 1 — локальный CLI

Без backend, базы, MCP и CI. Только шесть команд.

Порядок реализации — от простого к сложному, **три из пяти пишутся вообще без
ИИ**:

| # | Команда | Сложность | Модель |
|---|---|---|:---:|
| 1 | `repomind index` | обойти `docs/`, собрать frontmatter, записать JSON | ❌ |
| 2 | `repomind check` | список валидаций | ❌ |
| 3 | `repomind init` | развернуть шаблоны из пакета | ❌ |
| 4 | `repomind task` | конвертация docx + создание папки | ❌ |
| 5 | `repomind sync` | первый раз появляется LLM | ✅ |
| 6 | `repomind plan` | самый сложный промпт | ✅ |

Такой порядок удобен тем, что после четвёртого шага уже можно жить: структура
работает, валидация ловит ошибки, ТЗ загружаются. Модель подключается к готовому
скелету.

**Критерий готовности:** на реальном проекте задача проходит от `repomind task`
до зелёного `repomind check`, и постоянная документация меняется только там,
где реально изменилось поведение.

## Версия 2 — автоматизация

Всё спроектировано, включается по готовности.

### Хуки

Схема «дешёвое часто, дорогое редко»:

```text
правка файла   →  PostToolUse    →  touch .repomind/dirty     бесплатно
задача готова  →  TaskCompleted  →  repomind sync             1 вызов
перед коммитом →  git pre-commit →  repomind check            бесплатно
```

Первый уже лежит в примере: [.claude/settings.json](../examples/demo-project/.claude/settings.json).

⚠️ Не вешать sync на `Stop` — он срабатывает после каждого ответа модели.

### CI — можно включить в любой момент

Сознательно **не входит в первую версию**, чтобы не усложнять старт. Но всё для
этого готово: команды уже умеют работать в режиме без записи.

```bash
repomind init --with-ci
```

положит workflow примерно такого вида:

```yaml
on:
  pull_request:
    paths: ["backend/**", "frontend/**", "docs/**"]

jobs:
  documentation:
    steps:
      - checkout
      - install repomind
      - run: repomind check --strict
      - run: repomind sync --check-only --base origin/main
```

`--check-only` ничего не пишет: команда просто возвращает код 2, если
документация отстала от кода.

**Два режима, и путать их не надо:**

| Режим | Что делает | Когда включать |
|---|---|---|
| **Check** | сообщает, что устарело, проваливает PR | сразу, безопасно |
| **Fix** | создаёт патч или отдельный PR | по метке `docs:autofix`, вручную |

**CI не должен автоматически менять основную ветку.** Fix-режим вешается на
метку в PR — так у человека остаётся контроль над тем, когда модель пишет в
репозиторий.

Claude Code запускается в CI через `claude -p`, Codex — через `codex exec`;
у Codex есть официальный GitHub Action.

## Версия 3 — Jira и GitHub

Только здесь появляется MCP или прямая API-интеграция.

```text
Jira task  →  repomind task  →  реализация  →  PR  →  summary и result обратно в Jira
```

Тогда `docs/requirements/inbox/` перестаёт быть нужен для большинства задач —
ТЗ приезжает само.

**Критерий готовности:** ТЗ не копируется руками, а summary попадает в Jira без
участия разработчика.

## Версия 4 — командный сервис

Backend нужен **только** для:

- общей панели проектов;
- статистики покрытия документацией;
- централизованных правил;
- согласования ADR;
- работы между несколькими репозиториями;
- корпоративных политик;
- истории расходов моделей.

Всё, что можно оставить в Git, остаётся в Git. **Backend не становится
источником правды по документации** — источник правды всегда репозиторий.

## С чего начать лично тебе

Если ты раньше не настраивал агентов — не начинай с CLI. Порядок такой:

1. **Заведи `AGENTS.md` в рабочем проекте сегодня.** Двадцать строк: где что
   лежит, чем тестировать, как называть коммиты. Плюс `CLAUDE.md` с одной
   строкой `@AGENTS.md`. Эффект сразу, стоит ноль.
2. **Напиши один скилл.** Возьми процедуру, которую делаешь руками одинаково
   каждый раз, опиши в `.claude/skills/<имя>/SKILL.md`, вызови через `/имя`.
3. **Поставь один хук** — `PostToolUse` на `Edit|Write`, который пишет в лог.
   Убедись, что стреляет там, где ты думаешь.
4. **Размети блоками один существующий документ** — frontmatter с `code_paths`,
   маркеры `<!-- block: ... -->`. Посмотри, удобно ли.
5. **Только теперь** — `repomind index` и `check`.

К пятому шагу ты будешь понимать, зачем они, и напишешь их правильно.
