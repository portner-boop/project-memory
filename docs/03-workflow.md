# 03 — Полный цикл

```text
ЭТАП                 ЧТО ПРОИСХОДИТ                          КТО РАБОТАЕТ
────────────────────────────────────────────────────────────────────────
1. repomind task     ТЗ (.docx) → папка задачи               скрипт
2. repomind plan     разбор кода → deep-dive + estimate      МОДЕЛЬ ← вызов 1
3. разработка        пишем код по плану                      ты и агент
4. repomind sync     git diff → какие абзацы доков поправить МОДЕЛЬ ← вызов 2
5. применение        операции → markdown                     скрипт
6. repomind check    валидация                               скрипт
```

**Из шести этапов модель работает на двух.** Остальное — обычный код.

---

## Этап 1. Загрузка ТЗ

Полностью описан в [04 — CLI](04-cli.md#загрузка-тз). Коротко:

```bash
# кинул ABSHTRUE-657.docx в docs/requirements/inbox/
repomind task
```

Word конвертируется в markdown, ID вытаскивается из имени файла, папка задачи
создаётся, `docs/now/current-task.md` обновляется.

---

## Этап 2. Планирование

```bash
repomind plan ABSHTRUE-657
```

или из агента: `/docs-plan ABSHTRUE-657`

### Что делает скилл

1. Читает `request.md` — само ТЗ.
2. Читает `_index.json` — карту документации.
3. По тексту ТЗ прикидывает, какие модули затронуты.
4. Открывает **только** документы с пересекающимися `code_paths`.
5. **Читает реальный код** этих модулей — модели, сериализаторы, компоненты.
6. Пишет три файла.

Шаг 5 — принципиальный. План, построенный по одному ТЗ, бесполезен. Ценность
появляется, когда агент разобрал, **как оно работает сейчас**, и предложил
реализацию, которая ложится на существующую архитектуру.

Он же самый дорогой. Если рядом стоит [CodeGraph](07-codegraph.md), вместо
десятка `grep` и чтений файлов целиком делается один запрос:

```bash
codegraph explore "расчёт расходов по этапу отчёта"
```

и в контекст попадают только нужные функции с путями вызовов между ними.

### Что получается на выходе

| Файл | Для кого | Содержание |
|---|---|---|
| `deep-dive.md` | разработчик и агент | AS IS с путями и строками, рекомендуемая реализация с кодом, что затронем, риски, план, проверка |
| `estimate.md` | ты и менеджер | разбивка по частям, часы, допущения |
| `summary.md` | все остальные | 3 абзаца человеческим языком, без путей к файлам |

Живой образец нужного уровня детализации:

- [DEMO-657/deep-dive.md](../examples/demo-project/docs/tasks/DEMO-657/deep-dive.md)
- [DEMO-657/estimate.md](../examples/demo-project/docs/tasks/DEMO-657/estimate.md)
- [DEMO-657/summary.md](../examples/demo-project/docs/tasks/DEMO-657/summary.md)

### Обязательная структура `deep-dive.md`

Она зашита в [SKILL.md](../examples/demo-project/.agents/skills/docs-plan/SKILL.md):

```text
## Что нужно сделать          — требования по пунктам, из ТЗ
## Короткий вывод             — 5-8 тезисов: как ложится на архитектуру
## Как это работает сейчас    — AS IS, разделами по подсистемам, с path:line
## Рекомендуемая реализация   — по частям, с кодом, который надо написать
## Что конкретно затронем     — списки файлов по частям + «не трогаем»
## Риски                      — пронумерованные, с последствиями
## План реализации            — по частям, по шагам, включая тесты
## Проверка                   — команды + ручной сценарий
## Файлы                      — итоговый список
```

Раздел **«не трогаем»** экономит больше всего времени: он снимает вопросы «а не
надо ли ещё вот тут?» и защищает от лишних правок. Туда же идёт найденный
мёртвый код.

---

## Этап 3. Разработка

Агент идёт по чеклисту из `deep-dive.md` и отмечает пункты в `progress.md`.

Правило из `AGENTS.md`: **отклонился от плана — запиши, почему.**
Через месяц это единственный источник ответа на вопрос «почему сделали не так,
как планировали».

## Этап 4. Синхронизация — подробно

Самый непонятный момент, поэтому разберём на конкретном примере.

### Что вообще значит «синхронизировать»

У тебя есть постоянная документация. Ты только что поменял код. Вопрос:
**какие абзацы документации теперь врут?**

Ответ на этот вопрос и есть sync. Не «перегенерировать доки», а найти
устаревшие абзацы и поправить их.

### Исходная ситуация

В документации лежит:

```md
---
id: PRODUCT-REPORTS
code_paths:
  - backend/app/report/**
  - frontend/src/pages/ReportsPage.vue
last_verified_commit: 7c3e910
---

## Сортировка по умолчанию
<!-- block: REPORT.DEFAULT_SORTING -->

Отчёты выводятся в порядке добавления в базу.

## Статусы
<!-- block: REPORT.STATUSES -->

draft → open → review → closed.
```

Ты закоммитил изменение сортировки. Запускаешь:

```bash
repomind sync
```

### Шаг 4.1 — скрипт берёт diff

```bash
git diff --name-status origin/main...HEAD
```

```text
M  backend/app/report/repository.py
M  backend/app/report/service.py
M  frontend/src/pages/ReportsPage.vue
M  backend/tests/test_report_sorting.py
```

Модель тут ещё не участвует.

### Шаг 4.2 — классификация

Короткий вызов модели (или, для очевидных случаев, эвристика по diff):

```json
{
  "behavior": true,
  "api_contract": false,
  "database": false,
  "architecture": false,
  "configuration": false,
  "refactoring_only": false,
  "affected_paths": [
    "backend/app/report/repository.py",
    "backend/app/report/service.py",
    "frontend/src/pages/ReportsPage.vue"
  ]
}
```

**Здесь спрятана главная экономия.** Если `refactoring_only: true` — дальше не
идём вообще. Переименовал переменную → постоянную документацию трогать незачем,
дописали строчку в `result.md`, разошлись. Ноль дорогих вызовов.

### Шаг 4.3 — сопоставление с индексом

Скрипт берёт `affected_paths` и матчит их с `code_paths` из `_index.json`:

```text
backend/app/report/service.py
   ├─ PRODUCT-REPORTS  (backend/app/report/**)        ✅ совпало
   └─ ARCH-AUTH        (backend/app/auth/**)          ❌ мимо

frontend/src/pages/ReportsPage.vue
   └─ PRODUCT-REPORTS  (frontend/src/pages/Reports…)  ✅ совпало
```

Отобран **один** документ из всех, что есть в проекте.

**Ограничение масок.** Такой матчинг грубый: он пропускает транзитивные связи.
Поменяли общий хелпер `backend/app/common/periods.py#overlaps` — под маску
`backend/app/report/**` это не попадает, а документ про отчёты задет, потому что
расчёт вызывает этот хелпер.

С [CodeGraph](07-codegraph.md) добавляется второй проход — по графу вызовов:

```bash
codegraph impact backend/app/common/periods.py#overlaps
```

возвращает всё, что зависит от символа, и документы ищутся уже по этому списку.
Без CodeGraph работают только маски — грубее, но всегда.

### Шаг 4.4 — что уходит в модель

| Уходит | Не уходит |
|---|---|
| текст задачи ABSHTRUE-657 | весь репозиторий |
| хунки diff (`git diff -U3`) | вся документация |
| сигнатуры изменённых функций | другие задачи |
| **блоки только из `PRODUCT-REPORTS`** | git history |
| текущий `deep-dive.md` | |

Правая колонка — причина, по которой это работает на большом проекте.

### Шаг 4.5 — модель возвращает операции, а не текст

```json
{
  "status": "update_required",
  "operations": [
    {
      "action": "replace_block",
      "document_id": "PRODUCT-REPORTS",
      "block_id": "REPORT.DEFAULT_SORTING",
      "content": "Отчёты сортируются по дате начала периода по убыванию.\nЗаписи без даты — в конце списка.\n\nBackend: `backend/app/report/service.py#ReportService.get_all`.\nFrontend: `frontend/src/pages/ReportsPage.vue#defaultSort`.",
      "evidence": [
        "backend/app/report/repository.py#ReportRepository.list",
        "frontend/src/pages/ReportsPage.vue#defaultSort"
      ],
      "confidence": 0.94
    },
    {
      "action": "append_task_result",
      "task": "ABSHTRUE-657",
      "content": "Изменена сортировка отчётов..."
    }
  ]
}
```

Обрати внимание: блок `REPORT.STATUSES` в ответе **отсутствует**. Он не менялся —
модель его и не трогала.

### Шаг 4.6 — почему не дать модели просто писать в файлы

Потому что тогда её ничем не ограничить. Операцию можно проверить **до**
применения:

| Проверка | Если не прошла |
|---|---|
| `document_id` и `block_id` есть в индексе? | отказ |
| JSON соответствует схеме? | отказ, просим переделать |
| символы из `evidence` реально есть в изменённых файлах? | **отказ** |
| символ реально связан с изменением (только с CodeGraph) | **отказ** |

Последняя строка появляется, когда доступен граф: модель больше не может
сослаться на существующую, но не относящуюся к делу функцию. Переиндексация
при этом идёт [параллельно вызову модели](07-codegraph.md#параллельная-переиндексация-во-время-sync)
и по времени обходится в ноль.

Последнее — защита от главной болезни LLM: правдоподобного вранья.
**Утверждение без доказательства не применяется.**

Парное правило: если модель не может понять намерение из кода — она обязана
вернуть `mark_needs_review`, а не сочинить. Ты увидишь пометку в diff и
допишешь строчку сам за десять секунд. Это несравнимо дешевле, чем красивая
выдумка в архитектурном документе, которую через полгода примут за правду.

### Шаг 5 — применение

Скрипт находит в файле маркер `<!-- block: REPORT.DEFAULT_SORTING -->`, заменяет
текст до следующего маркера, обновляет `last_verified_commit`.

Результат в `git diff`:

```diff
 ## Сортировка по умолчанию
 <!-- block: REPORT.DEFAULT_SORTING -->

-Отчёты выводятся в порядке добавления в базу.
+Отчёты сортируются по дате начала периода по убыванию.
+Записи без даты — в конце списка.
+
+Backend: `backend/app/report/service.py#ReportService.get_all`.
+Frontend: `frontend/src/pages/ReportsPage.vue#defaultSort`.

 ## Статусы
 <!-- block: REPORT.STATUSES -->
```

Вот это и есть весь sync.

### Набор операций

| `action` | Что делает |
|---|---|
| `replace_block` | заменяет содержимое блока |
| `append_block` | дописывает в конец блока |
| `create_document` | создаёт новый документ с frontmatter |
| `create_adr` | создаёт ADR в `docs/decisions/` |
| `append_task_result` | дописывает `tasks/<ID>/result.md` |
| `mark_needs_review` | помечает блок, когда намерение неясно |

Статусы ответа: `no_changes` · `update_required` · `needs_review`.

## Когда документацию обновлять НЕ нужно

Самое важное правило для экономии. Большинство коммитов **не должны** менять
постоянную документацию.

### Не обновлять

переименование локальной переменной · форматирование · перенос функции без
изменения поведения · опечатка · внутренний тест · мелкий рефакторинг ·
изменение комментария

### Обновлять

пользовательское поведение · API · схема БД · форматы событий · конфигурация ·
способы запуска · архитектурные границы · бизнес-правила · внешние интеграции ·
требования безопасности · принятое техническое решение

### Матрица

| Что сделал | `tasks/<ID>/result.md` | `product/` `architecture/` `contracts/` | `decisions/` |
|---|:---:|:---:|:---:|
| рефакторинг без изменения поведения | ✅ | ❌ | ❌ |
| починил баг | ✅ | только если врало описание | ❌ |
| новая фича | ✅ | ✅ | если было решение |
| поменял API | ✅ | ✅ | если было решение |
| миграция БД | ✅ | ✅ | обычно ✅ |
| выбрал новую технологию | ✅ | ✅ | ✅ |
| сменил конфигурацию / запуск | ✅ | ✅ | ❌ |

**Большинство коммитов — первая строка.** Если система лезет в архитектурные
документы на каждый чих, ты её выключишь через неделю: шумный diff бесит
сильнее, чем устаревшие доки.

## Этап 6. Проверка

```bash
repomind check
```

Без всякой модели:

уникальность document ID · уникальность block ID · существование всех
`path#Symbol` · битые markdown-ссылки · ссылки на удалённые файлы · обязательные
файлы задачи на месте · соответствие JSON Schema · протухший
`last_verified_commit` · слишком большие документы · конфликтующие активные ADR

И финал:

```bash
git diff
```

**Никакого специального интерфейса.** Документация ревьюится там же и так же,
как код. Любой отдельный UI для доков — ещё одно место, куда никто не заходит.

## Когда что запускать

| Момент | Команда | Стоимость |
|---|---|---|
| правка файла (хук `PostToolUse`) | `touch .repomind/dirty` | 0 |
| задача готова (хук `TaskCompleted`) | `repomind sync` | 1 вызов модели |
| перед коммитом (git pre-commit) | `repomind check` | 0 |
| руками, когда захотел | любая | — |

⚠️ Не вешать sync на `Stop` — он срабатывает после **каждого** ответа модели.
Подробности в [01 — Как это работает](01-concept.md#hook--вот-что-реально-срабатывает).
