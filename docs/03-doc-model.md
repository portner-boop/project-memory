# 03 — Модель документации

Три кита модели: **атомарные блоки**, **ADR** и **генерируемый каталог**.

---

## 1. Атомарные блоки

Агенту редко нужен весь файл `architecture.md`. Ему нужны конкретные сведения:

- как устроена авторизация;
- где хранится документ;
- какой endpoint изменяется;
- почему выбрали Qdrant;
- какие ограничения есть у текущей задачи.

Поэтому документацию делим на блоки со **стабильными идентификаторами**.

````md
---
id: ARCH-AUTH
type: architecture
code_paths:
  - backend/app/auth/**
last_verified_commit: a91d2f4
---

# Авторизация

## Выдача токена
<!-- block: AUTH.ACCESS_TOKEN -->

Access token выдаётся после проверки логина и пароля.
Основная реализация: `backend/app/auth/service.py#AuthService.login`.

## Обновление токена
<!-- block: AUTH.REFRESH_TOKEN -->

Refresh token хранится в HTTP-only cookie.
Основная реализация: `backend/app/auth/service.py#AuthService.refresh`.
````

Агент обновляет **не весь документ, а блок `AUTH.REFRESH_TOKEN`**.

Что это даёт:

- меньше объём входного контекста;
- ниже риск переписать правильный текст;
- меньше конфликтов при мерже;
- меньше расход токенов.

### Frontmatter документа

| Поле                   | Обязательно | Назначение                                               |
| ---------------------- | ----------- | -------------------------------------------------------- |
| `id`                   | да          | стабильный идентификатор документа, уникальный в проекте  |
| `type`                 | да          | `product` / `architecture` / `contract` / `decision` / `task` |
| `code_paths`           | нет         | glob-пути кода, по которым документ считается затронутым  |
| `last_verified_commit` | нет         | коммит, на котором содержимое подтверждали в последний раз |

### Правила именования ID

- Документ: `SCREAMING-KEBAB`, например `ARCH-AUTH`, `PRODUCT-CONTESTS`.
- Блок: `DOC_SCOPE.BLOCK_NAME`, например `AUTH.REFRESH_TOKEN`.
- ID **не переименовываются** при рефакторинге текста. ID — это адрес,
  на который ссылается индекс, ADR и task-документы.

## 2. Ссылки на код: путь + символ, а не номер строки

Номера строк устаревают на первом же рефакторинге. Путь и символ намного
стабильнее.

```text
✅ backend/app/auth/service.py#AuthService.refresh
❌ backend/app/auth/service.py:142
```

Такая ссылка проверяется скриптом: файл существует, символ находится в файле.

## 3. ADR — журнал решений

Код показывает, **как сейчас работает** система. Но он не показывает:

- почему выбрали Redis;
- почему отказались от Celery;
- почему Markdown хранится в S3;
- почему документ делится именно так;
- почему определённое решение поставлено на паузу.

````md
---
id: ADR-014
status: accepted
task: ABSHTRUE-657
date: 2026-07-24
---

# Использовать Redis Streams вместо Celery

## Контекст

Нужна очередь обработки документов без отдельной Celery-инфраструктуры.

## Решение

Использовать Redis Streams и отдельный Python worker.

## Последствия

Плюсы:

- меньше инфраструктуры;
- Redis уже используется проектом.

Минусы:

- retry и dead-letter механику нужно реализовать самостоятельно.
````

### Когда создавать ADR

**Только при реальном архитектурном решении. Не на каждый рефакторинг.**

| Создавать ADR                            | Не создавать ADR                    |
| ---------------------------------------- | ----------------------------------- |
| выбор технологии / библиотеки / хранилища | переименование переменной           |
| отказ от ранее выбранного решения         | вынос функции в отдельный модуль    |
| смена архитектурной границы               | добавление теста                    |
| осознанная пауза («решили не делать»)     | изменение форматирования            |

### Статусы

`proposed` → `accepted` → `superseded` / `rejected` / `on-hold`

`repomind check` умеет находить конфликтующие активные решения — два
`accepted` ADR по одному предмету.

## 4. Каталог генерируется автоматически

В исходной идее каталог создаёт отдельный агент. Для нашей системы это лишняя
трата токенов. Каталог строится обычным скриптом из YAML-frontmatter:

```json
{
  "ARCH-AUTH": {
    "path": "docs/architecture/auth.md",
    "code_paths": ["backend/app/auth/**"],
    "blocks": [
      "AUTH.ACCESS_TOKEN",
      "AUTH.REFRESH_TOKEN"
    ]
  }
}
```

**LLM здесь вообще не нужна.** То же касается:

- проверки ссылок;
- существования файлов;
- уникальности ID;
- корректности frontmatter;
- поиска пустых разделов;
- проверки структуры Jira-папок;
- определения изменённых файлов.

Индекс — это точка входа агента в документацию: он читает `docs/_index.json`,
сопоставляет `code_paths` с изменёнными файлами и открывает только нужные
документы.

---

## 5. Типы документов

| Каталог              | Что хранит                                       | Кто основной читатель |
| -------------------- | ------------------------------------------------ | --------------------- |
| `docs/product/`      | обзор продукта, бизнес-правила                   | PM, агент, новый разработчик |
| `docs/architecture/` | как устроена система                             | агент, разработчик    |
| `docs/contracts/`    | API, события                                     | агент, интеграторы    |
| `docs/decisions/`    | ADR                                              | человек, агент при планировании |
| `docs/requirements/` | исходные ТЗ «как пришли»                         | человек               |
| `docs/tasks/<ID>/`   | всё по конкретной Jira-задаче                    | агент во время работы |
| `docs/now/`          | текущая активная задача                          | агент при старте сессии |

Ключевое различие: `docs/architecture/` и `docs/product/` — **постоянная**
документация, `docs/tasks/` — **временная**, привязанная к задаче. Правила,
что и когда обновлять, — в [07 — Политика обновления](07-update-policy.md).
