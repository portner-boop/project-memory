# 07 — Политика обновления документации

Это **самый важный документ для экономии**. Большая часть коммитов не должна
приводить к изменению постоянной документации вообще.

## Не нужно обновлять постоянную документацию

- переименование локальной переменной;
- форматирование;
- перенос функции без изменения поведения;
- исправление опечатки;
- добавление внутреннего теста;
- небольшой технический рефакторинг;
- изменение комментария.

## Нужно обновлять при изменении

- пользовательского поведения;
- API;
- схемы БД;
- форматов событий;
- конфигурации;
- способов запуска;
- архитектурных границ;
- бизнес-правил;
- внешних интеграций;
- требований безопасности;
- принятого технического решения.

## Что делать при обычном рефакторинге

Достаточно обновить:

```text
docs/tasks/ABSHTRUE-657/result.md
```

**Постоянные архитектурные документы не трогаются.**

## Матрица решений

| Тип изменения                | `docs/tasks/<ID>/result.md` | `docs/architecture/` `docs/product/` `docs/contracts/` | `docs/decisions/` |
| ---------------------------- | :-------------------------: | :-----------------------------------------------------: | :---------------: |
| рефакторинг без поведения    | ✅                          | ❌                                                       | ❌                |
| исправление бага             | ✅                          | только если менялось описанное поведение                 | ❌                |
| новая фича                   | ✅                          | ✅                                                       | если было решение |
| изменение API                | ✅                          | ✅ (`contracts/api.md`)                                  | если было решение |
| миграция БД                  | ✅                          | ✅ (`architecture/data-storage.md`)                      | обычно ✅         |
| выбор новой технологии       | ✅                          | ✅                                                       | ✅                |
| смена конфигурации / запуска | ✅                          | ✅                                                       | ❌                |

## Как это реализовано технически

Флаг `refactoring_only` в классификации изменений (см.
[06 — Основной flow](06-workflow.md#42-затем-классификация-изменений)) —
это короткое замыкание:

```text
refactoring_only == true
   → пропустить отбор блоков постоянной документации
   → единственная операция: append_task_result
   → LLM-вызов минимальный или не нужен вовсе
```

## Правило доказательности

Из `AGENTS.md`:

> Every documentation statement must reference changed code, a requirement
> or an explicit decision.

Каждая операция обязана нести `evidence` — ссылки вида
`path/to/file.py#Class.method`. Утверждение без доказательства не применяется.

## Правило «не угадывать»

> When intent cannot be determined from code, mark the item as `needs_review`
> instead of guessing.

Это дешевле, чем правдоподобная выдумка в архитектурном документе: человек
увидит `needs_review` в Git diff и допишет одну строку сам.

## Отдельно: `last_verified_commit`

Поле обновляется только когда содержимое блока действительно подтверждено
против кода. Если документ давно не подтверждали, `repomind check` покажет его
как устаревший — это не ошибка, а сигнал для планового аудита.
