# 01 — Концепция

## Позиционирование

> **RepoMind — инкрементальная память проекта для разработчиков и coding agents.**

Короткая формулировка для лендинга:

> **RepoMind — документация, которая развивается вместе с кодом.**

Ключевое уточнение: основной продукт здесь — **не генератор документации**, а
**инкрементальная память проекта для coding agents**. Генерация текста — побочный
эффект, а не цель.

## Откуда взялась задача

Текущий рабочий flow уже близок к правильной системе. В нём есть:

- документация проекта;
- исходные ТЗ;
- отдельная папка под каждую Jira-задачу;
- технический deep dive;
- упрощённое описание для PM;
- план реализации;
- инструкции для агента.

**Проблема ровно одна: вся система держится на ручной дисциплине.**

Ничто не гарантирует, что после мержа PR документация будет обновлена. Ничто не
подсказывает агенту, какие именно документы читать. Ничто не проверяет, что
ссылки в документации всё ещё указывают на существующий код.

## Идея

Превратить документацию из набора файлов в **машиночитаемую память проекта**,
которая:

1. хранится рядом с кодом;
2. разбита на небольшие независимые блоки;
3. обновляется по изменениям кода;
4. содержит историю решений;
5. загружает агенту только нужный контекст;
6. проверяется скриптами и моделью.

## Чего мы сознательно НЕ делаем

В исходном видео идея реализована через главный skill и несколько субагентов:
импорт, очистка, обновление терминов, каталога и проверка связей. Документы
делятся на обзор проекта, архитектуру, текущую работу, спецификации и журнал
решений.

Для массового продукта такая конструкция слишком тяжёлая:

- четыре субагента на каждую правку;
- постоянный gap-анализ;
- полный пересмотр документации после каждой задачи.

Нужна более простая модель:

```text
Git diff
   → определение влияния
   → обновление конкретных блоков документации
   → проверка
   → обычный Git diff для человека
```

## Итоговая формула

Не «главный умный агент с четырьмя субагентами», а **гибрид скриптов и одного
короткого вызова LLM**:

```text
Git и скрипты
    ↓
находят изменения и нужные документы
    ↓
один короткий вызов LLM
    ↓
возвращает структурированные операции
    ↓
скрипты применяют и проверяют изменения
    ↓
человек видит обычный Git diff
```

Распределение ответственности:

| Компонент   | Роль                                                        |
| ----------- | ----------------------------------------------------------- |
| `AGENTS.md` | короткие постоянные правила                                  |
| `CLAUDE.md` | импортирует `AGENTS.md`, ничего своего не хранит             |
| Skill       | хранит процесс: как выполнить задачу                         |
| Hook / CI   | запускает процесс: когда его выполнить                       |
| MCP         | подключается только для Jira, Confluence и внешних источников|
| Субагенты   | только для крупных задач, не для обычного sync               |

## Три сильные идеи, ради которых всё затевается

1. **Документация состоит из атомарных блоков.** Агенту редко нужен весь
   `architecture.md` — ему нужен конкретный блок. См. [03 — Модель документации](03-doc-model.md).
2. **Фиксируется не только состояние, но и решения.** Код показывает, *как*
   работает система, но не *почему*. Для этого — ADR. См. [03 — Модель документации](03-doc-model.md#adr--журнал-решений).
3. **Каталог генерируется скриптом, а не моделью.** LLM здесь не нужна вообще.
   См. [08 — CLI](08-cli.md).

## Главный экономический эффект

Расход токенов становится зависим **от размера изменения, а не от размера
проекта**.

Это возможно потому, что в модель отправляется только:

- Jira-задача;
- изменённые фрагменты кода;
- сигнатуры изменённых классов и функций;
- связанные блоки документации;
- текущий implementation plan.

И **не отправляется**:

- весь репозиторий;
- вся документация;
- все предыдущие задачи;
- полный Git history.
