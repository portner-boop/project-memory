# DEMO-657 — оценка

## Backend

**1. Поле `stage_expense` (DecimalField, null=True) в `StageExpenseSnapshot` + миграция** — `1h`

**2. Хелпер расчёта за период** — `1.5h`
Сумма `Expense.amount` по принятым отчётам с пересечением периодов
`[begins_at, ends_at]` отчёта и этапа.

**3. `stage_expense` (SerializerMethodField) в `StageExpenseSerializer`** — `1.5h`
Снапшот на принятом этапе, живой расчёт на непринятом, фолбэк при `NULL`.

**4. Расширение снапшота при принятии этапа** — `3h`
`save_snapshot_for_accepted_stage` — второе поле в `defaults`; проверка порядка
«снапшот до смены статуса»; тест на регрессию порядка.

**5. Management-команда доливки** — `1h`
dry-run по умолчанию / `--apply`, идемпотентная, `total_expense` не трогает.

**6. Backend-тесты** — `2h`
пересечение периодов (один и несколько отчётов, граничные даты) · `0` без
пересечений · не нарастающий итог · снапшот и чтение из него · доливка и её
идемпотентность · legacy считается так же · `assertNumQueries` не вырос.

**Итого backend: 10 часов**

## Ключевые допущения

- пересечение периодов — **включительные границы** (касание в один день =
  пересечение); зафиксировать с заказчиком;
- доливка для ранее принятых этапов считается по **текущим** данным принятых
  отчётов (п. 8 ТЗ);
- выгрузка в «Статистике» не дорабатывается — там сейчас нет таблиц расходов
  (п. 12 ТЗ);
- релизы backend и pdf-service катятся независимо, backend первым.

## Что может увеличить оценку

- если заказчик потребует согласованности с «Расход всего» при кривых периодах
  (риск 1 в разборе) — плюс проектирование и ~4 часа;
- если колонка понадобится в legacy-UI — плюс ~3 часа на второй компонент.
