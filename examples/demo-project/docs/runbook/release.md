# Релиз

## Порядок выкатки
<!-- block: RELEASE.ORDER -->

Три части релизятся **раздельно**. Порядок имеет значение:

```text
1. backend        (первым — он добавляет поля в JSON)
2. pdf-service    (шаблоны, читают эти поля)
3. frontend       (последним)
```

Почему так: pdf-service принимает сырой `dict` и лишние поля игнорирует,
а Jinja-фильтр `| default(0)` переживает отсутствующее поле. Поэтому
рассинхрон в эту сторону безопасен, в обратную — покажет нули.
См. [ADR-001](../decisions/ADR-001-pdf-service.md).

## Миграции и доливки
<!-- block: RELEASE.MIGRATIONS -->

Миграции применяются автоматически при старте контейнера backend.

Доливки данных — **вручную, после релиза**, и всегда в два прохода:

```bash
# 1. посмотреть, сколько записей затронет
kubectl exec deploy/backend -- python manage.py backfill_stage_expense

# 2. применить
kubectl exec deploy/backend -- python manage.py backfill_stage_expense --apply
```

Доливки идемпотентны: повторный запуск безопасен, заполняются только пустые
значения.

## Откат
<!-- block: RELEASE.ROLLBACK -->

Откат образа — штатный. **Откат миграции — нет.**

Если миграция добавляла nullable-поле (обычный случай) — старый код с ней
работает, откатывать схему не нужно, просто верни предыдущий образ.

Если миграция была разрушающей — откат только через восстановление дампа.
Поэтому разрушающие миграции разбиваются на два релиза: сначала добавить
новое, потом отдельным релизом удалить старое.
