# Фиксировать вычисляемые значения снапшотом при принятии этапа

## Контекст

Колонка «Расход всего» считается на лету из принятых отчётов. Пока этап не
принят, это правильно — данные ещё меняются.

Но после принятия этапа значение обязано «замереть»: куратор подписал отчёт с
конкретной суммой, и она не должна поехать из-за того, что позже приняли ещё
один отчёт за пересекающийся период.

## Решение

В момент принятия этапа результат живого расчёта записывается в отдельное поле
модели-снапшота. Сериализатор выбирает ветку по статусу этапа: не принят —
считаем, принят — читаем снапшот.

Снапшот пишется **до** смены статуса, иначе сериализатор уже уйдёт в
снапшот-ветку и зафиксирует нули.

## Последствия

Плюсы:

- принятый отчёт неизменен, спор с грантополучателем закрывается ссылкой на
  снапшот;
- живой расчёт остаётся простым, без версионирования данных.

Минусы:

- логика раздваивается: у каждого вычисляемого поля две ветки и два теста;
- при добавлении нового вычисляемого поля нужен ещё один столбец в снапшоте
  и доливка для ранее принятых этапов;
- порядок «снапшот до смены статуса» — неочевидная зависимость, легко сломать
  рефакторингом.

## Альтернативы

- **Хранить историю всех значений** (temporal table) — отвергнуто как
  избыточное: нужна только точка на момент принятия.
- **Запретить принимать отчёты за пересекающиеся периоды** — отвергнуто,
  противоречит регламенту заказчика.
