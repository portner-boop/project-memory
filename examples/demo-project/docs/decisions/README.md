# Решения (ADR)

> Этот файл создаёт `/docs-init`. Его можно править под свой процесс.

## Зачем это нужно

Код показывает, **как** работает система. Он никогда не показывает, **почему**
решили именно так.

Через полгода кто-то смотрит на отдельный PDF-сервис и думает: «зачем, можно же
было рендерить в Django?». Кода, который отвечает на этот вопрос, не существует.
Дальше два варианта: потратить час на археологию или переделать и наступить на
те же грабли.

ADR (Architecture Decision Record) — короткая запись, которая закрывает вопрос
за минуту.

## Когда писать

**Только на настоящее решение.**

| Пишем ADR | Не пишем |
|---|---|
| выбрали технологию, библиотеку, хранилище | переименовали переменную |
| отказались от ранее принятого подхода | вынесли функцию в модуль |
| сдвинули архитектурную границу | добавили тест |
| осознанно решили **не** делать | поправили форматирование |

Если писать на каждый рефакторинг — папка превратится в свалку, и её перестанут
читать. Это худший исход, чем отсутствие ADR вообще.

## Как завести

```bash
cp docs/decisions/_template.md docs/decisions/ADR-003-краткое-название.md
```

Номер — следующий свободный. Номера не переиспользуются, даже если решение
отменили.

Агент тоже умеет заводить ADR сам — операцией `create_adr` во время
`/docs-sync`, если во время задачи было принято решение.

## Статусы

```text
proposed  → обсуждается
accepted  → принято и действует
superseded → заменено другим ADR (указать каким)
rejected  → рассмотрели и отказались
on-hold   → отложено осознанно
```

Отменённый ADR **не удаляется** — у него меняется статус. Ценность как раз в
том, чтобы видеть отвергнутые варианты.

`/docs-check` ругается, если два `accepted` ADR противоречат друг другу по
одному предмету.
