# docs-do

Выполняет план из `deep-dive.md` **по шагам**, проверяя каждый шаг тестами
проекта. Заменяет `repomind do`, пока CLI нет.

Работает только когда план уже есть. Нет — сначала `/docs-plan`.

---

## Железные правила

1. **Один шаг за раз.** Не делай два пункта плана сразу, даже если они кажутся
   связанными. Смысл команды — в том, чтобы поломку было видно сразу и точно.
2. **После каждого шага — валидация.** Команды берутся из
   `docs/runbook/daily.md`. Не из головы.
3. **Упало — остановись.** Не переходи к следующему шагу и не «чини по пути»
   молча. Сообщи, что упало, и спроси.
4. **Отклонился от плана — запиши почему.** В `progress.md`, сразу, не в конце.
5. **План — не догма, но и не черновик.** Понял, что шаг неверный — остановись
   и скажи, а не переписывай план молча.

---

## Шаг 1. Прочитать план

- `docs/tasks/<TASK-ID>/deep-dive.md`, раздел «План реализации»
- `docs/tasks/<TASK-ID>/progress.md` — что уже сделано
- `docs/runbook/daily.md` — какими командами проверять

Если `TASK-ID` не назван — возьми из `docs/now/current-task.md`.

Определи, с какого пункта продолжать: первый неотмеченный в `progress.md`.

## Шаг 2. Определить команды валидации

Из `RUN-DAILY` возьми то, что относится к изменяемой части:

| Меняешь | Чем проверять |
|---|---|
| backend | тесты этого модуля + линтер |
| frontend | линтер + сборка |
| схема БД | тесты + проверка, что миграция создана |
| шаблоны | smoke-тест рендера |

Нет подходящей команды в runbook — **спроси**, не выдумывай.

## Шаг 3. Цикл по шагам

Для каждого пункта плана:

```text
1. сделать ровно этот пункт
2. прогнать валидацию для затронутой части
3. упало  → остановиться, показать вывод, спросить
   прошло → отметить [x] в progress.md, следующий пункт
```

После каждого пункта отчёт одной строкой:

```text
[3/7] ✅ Сериализатор: поле добавлено, 14 тестов прошли (2.1s)
```

При падении:

```text
[4/7] ❌ Снапшот при принятии этапа

    FAILED test_snapshot_before_status_change
    AssertionError: expected 45000, got 0

Похоже, снапшот пишется после смены статуса — это риск №4 из разбора.
Продолжать не буду. Чинить или пересмотреть шаг?
```

## Шаг 4. Финальная валидация

Когда все пункты отмечены — прогнать **весь** чеклист из
`RUN-DAILY` / `DAILY.PRE_COMMIT`, а не только команды затронутых частей.

Шаги проверялись по отдельности — это не гарантирует, что вместе всё работает.

## Шаг 5. Записать итог

В `progress.md`:

- все пункты отмечены;
- раздел «Отклонения от плана» — что пошло не так, как задумано, и почему;
- раздел «Появившиеся решения» — если по ходу приняли архитектурное решение,
  зафиксировать. Это кандидат в ADR.

Затем предложи: `/docs-sync`.

---

## Чего НЕ делать

- Не делать несколько пунктов разом ради скорости.
- Не пропускать валидацию, потому что «правка тривиальная».
- Не чинить упавший тест правкой самого теста, не спросив.
- Не переписывать план молча.
- Не обновлять постоянную документацию — это работа `/docs-sync`.
