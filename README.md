# RepoMind

**Документация проекта, которая обновляется сама — по коду, который ты только что написал.**

---

## Проблема, которая тебе знакома

У тебя в проекте есть `docs/`. Когда-то ты их писал. Сейчас там написано, что
конкурсы сортируются по алфавиту, хотя полгода назад это поменяли.

А ещё:

- новый разработчик читает доки и делает неправильно;
- Claude Code читает доки и делает неправильно;
- ты не пишешь новые доки, потому что старые всё равно врут;
- на каждую задачу ты руками собираешь контекст: что за модуль, где логика, что уже решали.

Обновлять документацию руками никто не будет. **Значит, это должно происходить само.**

## Что делает RepoMind

```text
Ты написал код  →  repomind sync  →  документация обновлена  →  git diff
```

Не «сгенерировал документацию с нуля», а **точечно обновил те абзацы, которых
коснулось изменение**. Поменял сортировку — обновился абзац про сортировку.
Переименовал переменную — не обновилось ничего, и правильно.

И вторая половина, ради которой всё затевалось:

```text
Кинул ТЗ в папку  →  repomind plan  →  готовый технический разбор + оценка в часах
```

Агент читает не весь репозиторий, а только те документы, которые связаны с
затрагиваемым кодом. Поэтому это быстро и дёшево даже на большом проекте.

## Как это выглядит: 5 минут

### 1. Ставим

```bash
uvx repomind init
```

Появляется папка `docs/` с готовой структурой, файл правил для агентов
`AGENTS.md`, и два скилла, которые понимают и Claude Code, и Codex.
Подробно, что именно создаётся — [docs/04-cli.md](docs/04-cli.md#repomind-init).

### 2. Кидаем ТЗ

Просто перетаскиваешь `.docx` из почты в папку:

```text
docs/requirements/inbox/ABSHTRUE-657.docx
```

```bash
repomind task
```

Word конвертируется в markdown, номер задачи вытаскивается из имени файла,
папка задачи создаётся. Никаких аргументов писать не надо.

### 3. Получаем разбор

```bash
repomind plan ABSHTRUE-657
```

На выходе — не «список файлов», а полноценный технический разбор:
как оно работает сейчас (с путями и номерами строк), как это делать,
что конкретно затронем, риски, план, проверка, **оценка в часах**.

Живой пример — [DEMO-657/deep-dive.md](examples/demo-project/docs/tasks/DEMO-657/deep-dive.md)
и [estimate.md](examples/demo-project/docs/tasks/DEMO-657/estimate.md).

### 4. Пишем код

Обычная работа. Агент идёт по плану, отмечает пункты.

### 5. Синхронизируем

```bash
repomind sync
```

Смотрит `git diff`, понимает, что изменилось по смыслу, и правит **только те
абзацы документации, которых это касается**.

```diff
  ## Сортировка по умолчанию
  <!-- block: REPORT.DEFAULT_SORTING -->

- Отчёты выводятся в порядке добавления.
+ Отчёты сортируются по дате начала периода по убыванию.
+ Записи без даты — в конце списка.
```

Три строки в diff. Не переписанный файл на 600 строк.

### 6. Проверяем

```bash
repomind check
```

Ловит битые ссылки на код, дубли идентификаторов, забытые файлы задачи —
без всякого ИИ, обычным скриптом.

## Почему это не превращается в генератор мусора

Четыре ограничения, которые важнее любого промпта:

| Ограничение | Что оно предотвращает |
|---|---|
| Модель видит **только изменённый блок**, а не весь файл | переписывание того, что не просили |
| Модель возвращает **операции**, а не текст файла | порчу разметки и структуры |
| Каждое утверждение обязано нести **ссылку на код** | правдоподобное враньё |
| Не поняла — пишет `needs_review`, **а не догадку** | тихую подмену фактов |

И финальный контроль: результат ты смотришь в **обычном `git diff`**.
Никакого отдельного интерфейса, который никто не откроет.
